# 10주차 2단계 — 조건부 실행 설계

비싼 검증을 언제 돌릴지 조건을 걸고, 스킵이 안전한 이유와 required 충돌이 없음을 남긴다.

| 항목                           | 상태                               |
| ------------------------------ | ---------------------------------- |
| 실행 조건 구현                 | 완료 — `.github/workflows/e2e.yml` |
| 경계 사례 확인                 | 완료 — 로컬 21개 조합              |
| flaky 정책                     | 완료                               |
| 실행·스킵·실패 PR 증거         | **미확보**                         |
| required 설정과 머지 차단 확인 | **미실시**                         |

---

## 1. 대상과 현재 상태

저비용·결정적 검증(lint · typecheck · unit·integration test · production build)은 `quality` workflow에서 **조건 없이 모든 PR**에 돈다. 1단계 기록 기준으로 네 구간 합의 **조건별 중앙값은 cold 40초 / warm 38초**다. warm 회차 하나는 23초로 흩어져 범위가 15초였다.

조건을 거는 대상은 **E2E**다. 1단계까지는 CI에서 실행되지 않았다. `pnpm check`에 `test:e2e`가 없었고, 브라우저 설치 step만 남아 있어 1단계에서 제거했다.

조건을 거는 근거는 **브라우저 설치 비용과 외부 저장소 장애 이력**이다. 1단계 로그에서 확인한 값이다.

| 근거                       | 값                                                      |
| -------------------------- | ------------------------------------------------------- |
| chromium + FFmpeg 다운로드 | 매 실행 186.6 MiB (`100% of 184.3 MiB` + 2.3 MiB)       |
| 설치 step 소요             | cold 중앙값 29.5초 / warm 중앙값 26초, 22~44초로 흩어짐 |
| 외부 의존                  | 패키지 인덱스 해시 검증 실패로 5회 연속 차단된 이력     |

E2E 자체 실행은 로컬 warm 기준 13개 테스트 9.7초다. **CI에서 E2E 전체가 얼마나 걸리는지는 아직 측정하지 않았다.** 절대 시간이 아니라, 외부 저장소에 의존하는 설치 단계를 필요할 때만 타는 것이 조건을 거는 근거다.

## 2. 실행 조건

### `on.paths`를 쓰지 않는 이유

`on.pull_request.paths`는 조건이 맞지 않으면 workflow 자체가 트리거되지 않는다. 그 workflow의 job을 required로 걸어두면 체크가 보고되지 않아 PR이 "체크 대기"에서 멈춘다.

그래서 **workflow는 모든 PR에서 트리거하고, 실행 여부는 job 단위로 판정**한다.

### 구조

```
e2e.yml  (모든 PR에서 트리거)
├─ changes       변경 파일 목록으로 실행 여부 판정
├─ e2e           changes.outputs.run == 'true' 일 때만 실행
└─ e2e-required  always() — required로 거는 대상
```

`e2e`가 아니라 `e2e-required`를 required로 건다. 이 job은 선행 job이 실패·스킵해도 결과 판정을 시도하므로 체크가 미보고 상태로 남지 않는다.

### 판정 방식 — 스킵 목록만 나열한다

실행 대상 경로를 나열하면, 목록에 없는 새 파일이 스킵된다. 정책을 지키려면 반대로 해야 한다.

> 실행 결과에 영향을 주지 않는 것으로 확인한 문서 경로만 생략한다. 분류하지 못한 변경은 실행 대상으로 처리한다.

**스킵 허용**

| 경로                         | 근거                                    |
| ---------------------------- | --------------------------------------- |
| `docs/rfc/**`                | RFC·측정 기록. 코드에서의 참조는 주석뿐 |
| `docs/assignments/**`        | 과제 원문. 코드에서의 참조는 주석뿐     |
| `docs/images/**`             | 문서용 이미지                           |
| `docs/*.md` (하위 폴더 제외) | `decisions-week*.md`, `eslint-rules.md` |
| `README.md`                  |                                         |

**스킵하지 않음**

| 경로               | 이유                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| `docs/assets/**`   | `src/app/api/_data/commerce.test.ts`가 `docs/assets/week-05-product-images.md`를 읽는다 |
| `docs/examples/**` | `.tsx`, `.css`가 있다                                                                   |
| `docs/fixtures/**` | 데이터로 쓰일 수 있어 확인하지 않았다                                                   |
| `docs/local/**`    | gitignore 대상이라는 사실이 실행 영향이 없다는 근거는 아니다                            |
| 그 밖의 모든 경로  | 확인하지 않았으므로 실행한다                                                            |

**확장자로 문서를 판정하지 않는다.** `\.md$` 같은 규칙을 쓰면 위 `docs/assets`의 `.md`가 스킵되고, 그 파일은 테스트가 실제로 읽는다.

### 목록 신뢰성

| 상황                                          | 처리                            |
| --------------------------------------------- | ------------------------------- |
| `changed_files`가 양의 정수가 아님            | **실패**                        |
| 목록이 비었거나 `changed_files`와 개수 불일치 | **실행**                        |
| 이름 변경                                     | `previous_filename`도 판정 대상 |

PR 파일 API는 최대 3,000개까지만 돌려준다. 목록이 불완전하면 스킵하지 않는다. 페이지는 `--paginate --slurp`로 받아 `flat()`으로 합친다.

파이프 없이 파일로 받아 Node에서 배열 전체를 판정한다. `grep -q`로 조기 종료하면 앞 단계가 SIGPIPE로 실패해 실행 대상인데도 스킵으로 갈 수 있고, 파일명에 줄바꿈이 있으면 줄 단위 처리도 어긋난다.

## 3. 스킵이 안전한 이유

**"다른 검증이 E2E의 범위를 대신 잡는다"가 근거가 아니다.** 그렇게 주장하려면 각 검증이 실제로 무엇을 잡는지 확인해야 하는데, 이번 단계에서 확인하지 않았다.

이 설계에서 스킵이 안전한 근거는 **필터가 보수적이라는 데 있다.**

1. 스킵 허용 목록은 **확인 시점에 실행 결과에 영향을 주지 않는 것으로 확인한 문서 경로**만 담는다.
2. **추가·변경 파일의 경로와 이름 변경 전 경로 중 하나라도 허용 목록 밖이면 실행한다.**
3. 목록이 불완전하거나 판정이 이상하면 실행하거나 실패한다.

허용 디렉터리의 현재 용도를 확인한 것이지, 그 아래에 앞으로 추가되는 모든 파일의 실행 영향까지 보장하는 것은 아니다. 허용 경로 안에 새 파일이 생기거나 실행 코드가 문서를 읽도록 바뀌면 **허용 목록을 다시 검토한다.**

즉 **스킵되는 PR은 E2E가 검증하는 대상이 바뀌지 않은 PR로 한정된다.** 깨진 코드가 스킵을 타고 들어오려면 위 세 가지를 모두 통과해야 하는데, 그러려면 스킵 허용 목록 안의 문서 파일만 바뀌어야 한다.

### 이 E2E는 사전 검증이다

`playwright.config.ts`의 `webServer`가 로컬에서 `next build && next start`를 띄운다. 배포 URL을 요구하지 않으므로, 이 E2E는 **9주차 완료 기준(배포된 실행환경에서 핵심 흐름 확인)에 대한 사전 검증**이다.

두 층을 구분한다.

| 층                  | 무엇                                  | 실패 시 중단할 단계 |
| ------------------- | ------------------------------------- | ------------------- |
| 사전 검증 (이 단계) | 로컬 production 서버 대상 E2E         | 머지                |
| 완료 검증           | 배포된 Preview URL에서 핵심 흐름 확인 | Production 배포     |

**여기서 조건부로 스킵하는 것은 사전 검증이지 9주차의 완료 기준이 아니다.** Preview 검증은 별도로 충족해야 하며, **이번 단계에서는 그 구현과 충족 여부를 확인하지 않았다.** 스킵이 완료 기준을 대신하지 않는다는 구분만 기록해 둔다.

## 4. required 충돌 방지

`e2e-required`는 **정상 실행과 의도한 스킵만 성공으로 처리**한다. `always()`는 선행 job이 실패·스킵해도 판정을 시도하게 하는 설정이며, 항상 성공을 보고한다는 뜻이 아니다. workflow 자체가 취소되면 이 job도 함께 취소된다.

| `changes` | 실행 대상      | `e2e`                       | 판정     |
| --------- | -------------- | --------------------------- | -------- |
| `success` | `false`        | `skipped`                   | **성공** |
| `success` | `true`         | `success`                   | **성공** |
| 그 외     | 누락·오류 포함 | 실패·취소·예상 밖 스킵 포함 | **실패** |

### 왜 머지 차단으로 두는가

재현 환경(어디서 검증하는가)과 차단 여부(실패했을 때 무엇을 멈추는가)는 다른 축이다. 차단 여부는 네 가지로 판단한다.

| 기준        | 이 검증의 경우                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------- |
| 실패 영향   | 인증·주문·상품 목록 등 사용자 흐름이 깨진 채 `main`에 들어간다                                     |
| 검증 신뢰도 | 같은 코드에서 결과가 재현된다. 흔들리는 케이스는 6절의 flaky 기록으로 분리                         |
| 실행 비용   | 조건부 실행으로 문서 변경 PR에서는 **E2E 설치·실행 비용을 생략한다**(`changes`와 guard는 실행된다) |
| 대체 검증   | 실행된 회차에서는 이 검증을 대신할 지점을 확인하지 않았다                                          |

**현재는 실패 결과를 보고할 뿐 머지를 막지 않는다.** 이 저장소에는 branch protection도 ruleset도 없어 required check가 하나도 없다. 9절의 확인을 마친 뒤 `e2e-required`를 required로 설정해, 실행된 회차가 실패하면 머지를 차단하도록 한다. 스킵된 회차는 실행 대상이 아니므로 막을 것이 없다.

## 5. 경계 사례 확인 (로컬)

조합별 판정은 로컬에서 확인했다. 실제 PR 실행은 9절의 세 가지만 쓴다. 불필요한 CI 실행을 줄이려는 것이다.

**확인 방법** — `.github/workflows/e2e.yml`에 들어 있는 스크립트를 그대로 꺼내 실행했다. workflow와 다른 사본을 만들지 않으려는 것이다.

```bash
# 경로 판정: e2e.yml의 decide.cjs 본문을 추출해 pages.json·CHANGED를 바꿔가며 실행
#   CHANGED=<n> GITHUB_OUTPUT=out.txt node decide.cjs
# guard 판정: e2e-required의 run 블록을 추출해 환경 변수 조합으로 실행
#   CHANGES_RESULT=<r> RUN_TARGET=<t> E2E_RESULT=<e> bash guard.sh
```

아래 표의 입력은 각각 `pages.json`의 파일 목록과 세 환경 변수 값이다.

### 경로 판정 11개

| 케이스                      | 결과      |
| --------------------------- | --------- |
| 문서만 (`docs/rfc/`)        | 스킵      |
| 문서 + 코드                 | 실행      |
| `docs/assets/`              | 실행      |
| `docs/examples/`            | 실행      |
| `docs/local/`               | 실행      |
| 이름 변경 `src/` → `docs/`  | 실행      |
| 목록 절단 (받은 1 / 선언 5) | 실행      |
| 빈 목록                     | 실행      |
| `changed_files=0`           | **실패**  |
| `changed_files` 비정상      | **실패**  |
| 페이지 2개 합침             | 정상 판정 |

### guard 판정 10개

| 조합 (`changes`/대상/`e2e`)  | 결과     |
| ---------------------------- | -------- |
| `success`/`false`/`skipped`  | **성공** |
| `success`/`true`/`success`   | **성공** |
| `success`/`true`/`failure`   | 실패     |
| `success`/`true`/`cancelled` | 실패     |
| `success`/`true`/`skipped`   | 실패     |
| `success`/`false`/`success`  | 실패     |
| `failure`/—/—                | 실패     |
| `cancelled`/—/—              | 실패     |
| `success`/`""`/—             | 실패     |
| `success`/`maybe`/—          | 실패     |

성공은 허용한 두 조합뿐이다.

## 6. flaky 정책

| 항목        | 규칙                                                                                                                                         |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 재시도 횟수 | `retries: process.env.CI ? 2 : 0` 유지. 로컬은 재시도 없이 즉시 드러나게 두고 CI만 재시도한다. 값을 바꿀 근거가 없어 기존 설정을 그대로 둔다 |
| 기록        | JSON 리포터 결과에서 `status === 'flaky'`인 항목을 **Actions 실행 요약**에 남긴다. 원본 리포트와 `test-results/`는 아티팩트로 14일 보존한다  |
| 격리        | **자동 격리하지 않는다.** `test.fixme`는 검증을 생략하므로, 격리 사유·담당자·복구 조건을 정한 뒤에 적용한다                                  |

리포터를 `list` 하나에서 `list` + `json`으로 바꿨다. `list`는 실행 중 사람이 읽는 용도, `json`은 집계용이다. JSON 리포트에는 trace가 들어가지 않아 `test-results/`를 함께 보관한다.

리포트 상태를 세 가지로 구분한다.

| 상태           | 기록                                                   |
| -------------- | ------------------------------------------------------ |
| JSON 있음      | flaky 목록 또는 "재시도로 통과한 테스트 없음"          |
| JSON 없음      | "E2E 리포트 미생성" — 원인은 선행 step 로그로 확인한다 |
| 읽기·파싱 실패 | "flaky 리포트 처리 실패" 기록 후 **step 실패**         |

`$GITHUB_STEP_SUMMARY`는 Actions 실행 요약 화면이다. PR 화면에 직접 출력되지는 않는다.

## 7. 도입하지 않은 것

| 항목          | 판단                                                                                                                                                                                      |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 브라우저 캐싱 | **보류.** 다운로드 186.6 MiB는 캐싱 이득의 근거가 아니다. 복원 비용과 비교해야 하고, `--with-deps`가 설치하는 시스템 의존성은 그 캐시에 포함되지 않아 apt 실패는 캐싱으로 해결되지 않는다 |
| merge queue   | **미도입.** 이번 범위에서는 병합 대기열의 통합 검증까지 도입하지 않는다                                                                                                                   |
| label 트리거  | 미도입. 사람이 매번 붙여야 해 스킵 판단이 사람에게 남는다                                                                                                                                 |
| draft skip    | 미도입. 경로 판정과 목적이 겹친다                                                                                                                                                         |

## 8. 검증별 실행 배치 갱신

이번 단계에서 확정된 값이다.

| 검증                       | 성격              | 실행 위치 | 실행 조건             | 실패 시 중단할 단계 (계획)  |
| -------------------------- | ----------------- | --------- | --------------------- | --------------------------- |
| E2E (로컬 production 서버) | 사전 검증 (9주차) | CI        | 문서 변경만이 아닌 PR | 머지 (guard `e2e-required`) |

**"실패 시 중단할 단계"는 계획값이다.** required가 설정되기 전까지는 실패 결과가 보고될 뿐 머지가 막히지 않는다(9절 참고).

저비용 검증(lint · typecheck · unit·integration test · production build)은 조건 없이 모든 PR에서 돈다. 실행 조건은 1단계에서 바뀌지 않았고, 차단 여부는 위와 같이 required 설정 이후의 효과다.

## 9. 남은 것

### 실행 증거 (미확보)

| #   | 확인                         | 방법                                   |
| --- | ---------------------------- | -------------------------------------- |
| 1   | 조건에 걸리는 PR에서 실행    | `src/` 변경 PR                         |
| 2   | 조건에 안 걸리는 PR에서 스킵 | `docs/rfc/` 만 변경한 PR, guard는 성공 |
| 3   | E2E 실패 시 guard도 실패     | 테스트를 의도적으로 깨뜨린 PR          |

### required 설정 (미실시)

확인 시점에 이 저장소에는 branch protection도 ruleset도 없어 **required check가 하나도 없다.** 구현과 위 확인이 끝난 뒤 설정한다.
