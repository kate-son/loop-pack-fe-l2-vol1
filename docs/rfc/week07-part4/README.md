## 2부. LCP 구간 비교 — 숫자보다 "무엇이 LCP였나"가 핵심

## LCP element가 바뀌었다

|                      | Before                                                          | After                                  |
| -------------------- | --------------------------------------------------------------- | -------------------------------------- |
| 홈 LCP element       | `h2#week07-hero-title` — **"매일 새롭게 발견하는 취향" 텍스트** | `section.hero > img` — **hero 이미지** |
| 상품목록 LCP element | `h2#week07-hero-title` — **"상품 목록" 텍스트**                 | hero 이미지                            |

**Before에서는 hero가 한 번도 LCP가 되지 못했다.** Lighthouse의 `network-requests`가 그 이유를 보여준다.

|                            | Before 홈                       | Before 상품목록     | After                     |
| -------------------------- | ------------------------------- | ------------------- | ------------------------- |
| hero 요청 완료(`finished`) | **`0`(미완료)**                 | **`false`(미완료)** | ✅ 완료                   |
| 측정 창 안에서 받은 양     | **682,096 bytes (전체의 9.0%)** | 약 7,274KB          | 홈 163.7KB / 목록 132.4KB |
| 전체 파일 크기             | 7,545,239 bytes                 | 7,545,239 bytes     | —                         |

`lcp-breakdown-insight`도 같은 이야기를 한다.

| 구간                       | Before 홈     | After 상품목록 |
| -------------------------- | ------------- | -------------- |
| Time to first byte         | 4ms           | 9ms            |
| Resource load delay        | —             | 581ms          |
| **Resource load duration** | **항목 없음** | 2,422ms        |
| Element render delay       | 3,733ms       | 27ms           |

**Before에는 `Resource load duration` 항목 자체가 없다** — LCP가 이미지가 아니라 텍스트였기 때문에 이미지 로딩 구간이 잡히지 않는다.

### 그래서 상품목록의 "LCP +1,176ms"는 악화가 아니다

Before의 LCP 1,444ms는 **작은 텍스트가 LCP였을 때의 값**이고, After의 2,620ms는 **거대한 hero 이미지가 완전히 로드된 시점**이다. 측정 대상이 다르므로 이 둘을 뺄셈해 "느려졌다"고 말할 수 없다.

같은 페이지에서 **Speed Index가 12,502ms → 2,310ms로 81.5% 줄었다**는 것이 실제 사용자 체감을 보여준다. Speed Index는 화면이 시각적으로 채워지는 과정 전체를 적분한 값이라, 7.5MB 이미지가 progressive JPEG로 12초 넘게 서서히 채워지던 Before의 상태를 정확히 반영한다.

Part 0에서 사용자가 관찰한 "47.6초 녹화 내내 hero가 LCP로 갱신되지 않음"이 이번에도 재현되는지 확인했다.

|                      | Before 홈                              | After 홈               |
| -------------------- | -------------------------------------- | ---------------------- |
| FCP                  | 624.9ms                                | 617.6ms                |

## 4부. 효과가 없거나 악화된 변경

완료조건이 "효과가 없거나 악화된 변경은 되돌리거나, 유지하는 이유를 기록"을 요구한다.

| 변경                                           | 판정                                                                                                                           | 처리                                                                                                           |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| **Round 1** `layout.css` 전역 import 통합      | 효과 없음 — 합쳤더니 `PageHeading.module.css`가 그 자리를 채워 render-blocking 요청 수가 그대로였다                            | **유지.** 중복 import를 정리한 것 자체는 옳고, 되돌릴 이유가 없다. 실패 기록으로 남김                          |
| **Round 8** 이미지 캐시 TTL 60초 → 1일         | 진단이 틀렸음 — 실제 원인은 변환 비용이 아니라 대역폭 경쟁이었다(Round 10에서 확인). 효과 측정도 없었다                        | **철회.** `next.config.ts`를 기본값으로 되돌림. 시도 경위와 변환 비용 실측(232ms vs 1.6ms)은 기록 유지         |
| **Round 10** 카드 이미지 `fetchPriority="low"` | 의도대로 동작(카드가 hero 뒤로 밀림: 1,205ms → 3,194ms)했으나 **점수는 안 움직임** — 카드가 병목이 아니었다                    | **유지.** LCP 요소가 아닌 이미지의 우선순위를 낮추는 것은 그 자체로 옳은 방향이고, 회귀도 없다                 |
| **Round 11** `sizes`에 `1170px` 선언           | DPR을 1.75로 오독한 결과 — 실제 DPR 2에서는 `w=2400`이 정확한 값이라 오버슛이 애초에 없었다                                    | **철회.** 실제 렌더 폭 `1200px`로 정정. 여백 32px을 반영한 부분은 정당하므로 유지                              |
| **Round 7** 스켈레톤 도입                      | 한때 "LCP 432ms 악화"로 의심 → **측정 조건(이미지 캐시) 미통제로 인한 오판**이었다. 대조 실험에서는 오히려 개선(LCP 700→582ms) | **유지.** 요구사항인 "목록 크기를 예상할 수 있는 pending UI"를 충족하고, 기하가 1px 차이라 CLS도 만들지 않는다 |

**FCP만 줄고 다른 지표가 나빠진 경우는 없었다.** 오히려 FCP는 Before/After가 사실상 동일하고(1,395 → 1,388ms, 측정 범위와 비슷한 크기), 개선은 LCP·Speed Index에 집중됐다.
