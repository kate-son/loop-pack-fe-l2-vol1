# 10주차 1단계 — CI 파이프라인 측정·최적화

1단계의 0~3단계 실행 기록이다. 측정 조건, 원시값, 실행 로그, 판단 근거를 이 문서 안에 둔다.

| 단계 | 내용                       | 상태                                    |
| ---- | -------------------------- | --------------------------------------- |
| 0    | Before 고정                | 측정 실행 확보 — 캐시 조건 증거 확인 중 |
| 1    | 병목에 맞는 전략만 적용    | 미착수                                  |
| 2    | 캐시 동작 확인             | 미착수                                  |
| 3    | 같은 조건에서 After 재측정 | 미착수 — cold·warm 각 3회               |

**남은 것**

1. **캐시 조건 증거.** 회차별 cold/warm 분류가 아직 시간 패턴에 근거한 잠정값이다. 확정하려면 각 attempt의 `Set up Node.js`·`Post Set up Node.js` 로그에서 복원된 key와 저장·생략 메시지를 읽어야 한다. 추가 실행이 아니라 **이미 확보한 13회의 로그**를 확인하는 일이다.
2. **표본 선택 기준.** cold로 분류한 성공 회차가 5회인데 어느 범위를 기준선으로 쓸지 정하지 않았다. 사전에 정한 규칙이 없으므로, 조건이 확인된 유효 표본 전체를 쓰거나 특정 회차를 제외할 환경 차이를 제시해야 한다.

---

## 0단계 — Before 고정

### 0-1. 계측 구성 변경

`pnpm check`가 단일 step이라 내부의 test·lint·typecheck·build 소요가 Actions 로그에서 구분되지 않았다. 구간을 보려면 계측이 필요한데, 이를 After에만 넣으면 Before와 조건이 달라져 시간 차의 원인을 가릴 수 없다. 그래서 **Before 측정 시점부터 step을 나누고 After까지 같은 구성을 유지한다.**

`.github/workflows/quality.yml` 변경:

```diff
-      - name: Run quality checks
-        run: pnpm check
+      - name: Test
+        run: pnpm test
+      - name: Lint
+        run: pnpm lint
+      - name: Typecheck
+        run: pnpm typecheck
+      - name: Build
+        run: pnpm build
```

실행 순서와 검증 집합은 `pnpm check`와 같다. `package.json`의 `check` 스크립트는 로컬 실행용으로 그대로 둔다.

같은 커밋에서 job에 `timeout-minutes: 10`을 추가했다. 멈춘 job이 러너를 무한히 잡고 있지 않도록 상한을 두는 것이고, 관측된 최장 실행 시간 114초보다 여유를 두어 10분으로 설정했다. 이 값은 Before와 After에서 동일하게 유지한다.

이 변경으로 `pnpm` 기동이 5회(`check` 1회 + 하위 4회)에서 4회로 줄어든다. **이 차이를 최적화 성과로 계산하지 않는다** — 계측은 Before와 After에 동일하게 적용되므로 두 값 모두에 같은 방향으로 작용한다.

#### 계측 방식을 step 분리로 정한 근거

| 방식                 | 해상도 | 값 회수                                 | 저장소에 남는 계측 코드 |
| -------------------- | ------ | --------------------------------------- | ----------------------- |
| **step 분리** (채택) | 1초    | Actions API, 인증 없이 조회 가능        | 없음                    |
| 로그 타임스탬프 출력 | 밀리초 | raw 로그 열람 필요 (현재 인증 없이 403) | workflow 또는 스크립트  |

이번 단계는 cold·warm 각 3회씩 Before/After 총 12회를 같은 조건으로 반복해 raw·중앙값·범위를 남기는 작업이다. step 분리는 `/actions/runs/{id}/jobs`가 step별 `started_at`·`completed_at`을 돌려주므로 집계가 자동으로 되고, 타임스탬프 방식은 매 회 수동 확인이 붙는다. 반복 횟수가 많을수록 옮겨 적는 과정에서 값이 섞일 여지도 커진다.

**대가**: 해상도가 1초다. 16초를 넷으로 나누면 각 구간이 2~8초대일 텐데, 3초 구간의 ±1초는 비율로 33%다. 이 오차는 반복 측정의 범위에 흡수되지 않는 계통 오차라, 구간들이 비슷하게 나와 순위가 갈리지 않으면 타임스탬프 출력을 덧붙여 확인한다.

### 0-2. 측정 조건 고정

Before와 After에서 아래 조건을 모두 동일하게 유지한다. 다른 것은 commit SHA와 캐시 상태(cold/warm)뿐이다.

#### 트리거와 비교 범위

| 항목      | 고정값                                                              |
| --------- | ------------------------------------------------------------------- |
| 트리거    | `pull_request` 이벤트                                               |
| 비교 범위 | `pnpm check`가 실행하는 검증 집합 (test · lint · typecheck · build) |
| 러너      | `ubuntu-latest`                                                     |
| Node 버전 | `.nvmrc` 기준 (24.17.0)                                             |
| pnpm 버전 | `package.json#packageManager` 기준 (10.15.1)                        |

현재 실행 이력은 전부 `push`/`main` 이벤트이고 `pull_request` 실행 이력이 없다. 측정 대상이 PR 검증이므로 트리거를 PR로 통일한다.

**E2E는 이 단계의 비교 범위에 넣지 않는다.** 검증 항목이 늘어나면 실행 시간 변화가 최적화의 결과인지 작업량 증가의 결과인지 구분되지 않는다. E2E 추가는 2단계에서 다룬다.

#### cold / warm 정의

측정 대상은 **PR #1의 CI 실행**이고, 조작 대상은 **그 PR의 캐시(`refs/pull/1/merge` 스코프)**다.

| 조건 | 준비                              |
| ---- | --------------------------------- |
| cold | 해당 PR의 캐시를 삭제한 뒤 실행   |
| warm | 해당 PR의 캐시를 유지한 채 재실행 |

측정할 때마다 **삭제한 캐시의 key와 id를 기록한다.** 조건이 실제로 성립했는지는 그 실행의 캐시 복원·미복원 로그로 확인한다.

#### 조건 판별의 근거 — 미확정

**확정에 필요한 증거는 로그다.** `actions/setup-node`는 복원된 key가 primary key와 같으면 저장을 생략하고 그 이유를 로그에 남긴다. 따라서 회차별 조건을 확정하려면 `Set up Node.js`의 복원 메시지(복원된 key)와 `Post Set up Node.js`의 저장·생략 메시지를 읽어야 한다. **이 로그는 인증 없이 403이라 아직 확보하지 못했다.**

현재 분류는 아래 세 가지 정황에 근거한 **잠정값**이다. 세 가지가 서로 어긋나지 않지만, 어느 것도 저장·복원 분기가 실행됐다는 직접 증거는 아니다.

| 정황                       | 내용                                                                                      |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| 작성자 확인                | cold 회차(att 1~4)는 재실행 전에 매번 캐시를 삭제했고, 이후 회차는 삭제하지 않았다        |
| `Post Set up Node.js` 소요 | 4–6초인 회차와 0초인 회차로 갈린다. 저장이 일어났는지 시사하지만 소요 시간일 뿐이다       |
| PR 캐시 생성·접근 시각     | `created 18:14:57`는 att12 종료 시점, `last_accessed 18:16:25`는 att13 실행 구간과 겹친다 |
| 시간 패턴                  | cold로 분류한 회차는 `Set up Node.js` 5–6s·`Install` 5–7s, warm은 8–12s·2s                |

**시간 패턴만으로 조건을 판별하면 캐시 효과 분석이 순환한다** — 시간으로 조건을 나눈 뒤 그 시간 차이를 캐시 효과로 설명하는 구조가 되기 때문이다. 아래 요약값은 이 잠정 분류가 맞다는 전제 위에 있다.

#### 기록 항목

| 항목              | 설명                                                     |
| ----------------- | -------------------------------------------------------- |
| 전체 실행 시간    | job 시작부터 종료까지 (대기열 시간은 포함하지 않는다)    |
| 러너 총 사용 시간 | 모든 job의 소요 합 (job을 나누면 이 값과 위 값이 갈린다) |
| step별 소요       | Actions API의 step `started_at`·`completed_at`           |
| 캐시 복원 결과    | 복원 여부, 복원된 key, 복원 메시지                       |
| 실행 식별자       | run URL, run ID, attempt 번호                            |
| commit SHA        | Before/After 각각                                        |
| 삭제한 캐시       | cold 실행 시 지운 key와 ref                              |

cold 3회 이상 / warm 3회 이상을 각각 재고 **raw 값·중앙값·범위**를 모두 남긴다. GitHub 러너 성능이 실행 시점에 따라 흔들리므로, 1회 값으로는 이후 변화가 개선인지 측정 흔들림인지 구분되지 않는다. Before와 After 모두 이 회차 수를 유지한다.

### 0-3. 측정 전 확인한 사항

- Actions 실행 이력 7회는 전부 `push`/`main` 이벤트이고 `pull_request` 실행 이력이 없다.
- PR 첫 실행 뒤에는 그 PR의 캐시가 새로 생기므로, cold 회차마다 이 캐시를 삭제한다. 조건 성립 여부는 그 실행의 캐시 복원 로그로 확인한다(0-2 참고).
- `concurrency` 설정이 없다. 같은 PR에 연속 push가 들어오면 이전 실행이 그대로 남는다.

#### 측정 저장소를 fork로 두는 이유

과제 제출은 upstream(`loopers-labs`)에 PR을 여는 방식인데, 그곳은 수강생 공용 저장소라 측정에 맞지 않는다. 확인 시점에 다른 PR의 캐시 19개가 있었고, 캐시 삭제 권한이 없어 **cold 조건을 만들 수 없다.** 다른 PR의 캐시를 지우는 것도 하면 안 되는 일이다. 동시 실행이 많아 러너 조건도 흔들린다.

그래서 0-5의 Before/After 측정은 **fork(`kate-son`)에서 연 PR로 수행한다.** 과제가 요구하는 것은 같은 조건에서 잰 Before/After이고, 측정 저장소가 fork라는 사실은 여기에 기록해 둔다. 제출 PR은 upstream에 별도로 연다.

### 0-4. 로컬 사전 확인 (참고값)

목적은 두 가지다. 네 명령이 분리된 상태에서 모두 통과하는지 확인하는 것, 그리고 구간 비율의 대략을 미리 보는 것이다. **Before 값이 아니며, CI 측정과 직접 비교하지 않는다.**

| 항목      | 값                                    |
| --------- | ------------------------------------- |
| 기준 커밋 | `051307a4` + 워크플로 변경(작업 트리) |
| Node      | v24.17.0                              |
| pnpm      | 10.15.1                               |
| OS·CPU    | macOS 26.5 / Apple M5 (arm64, 10코어) |
| 캐시 상태 | warm (`node_modules`·`.next` 존재)    |

#### 구간별 소요 — 3회

| 명령             | run 1   | run 2   | run 3   | 중앙값       | 범위  |
| ---------------- | ------- | ------- | ------- | ------------ | ----- |
| `pnpm test`      | 6,027ms | 6,063ms | 6,104ms | **6,063ms**  | 77ms  |
| `pnpm lint`      | 1,901ms | 1,863ms | 1,958ms | **1,901ms**  | 95ms  |
| `pnpm typecheck` | 876ms   | 893ms   | 920ms   | **893ms**    | 44ms  |
| `pnpm build`     | 3,724ms | 3,566ms | 3,639ms | **3,639ms**  | 158ms |
| 회차별 합계      | 12,528  | 12,385  | 12,621  | **12,528ms** | 236ms |

세 회차 모두 네 명령이 통과했다. 로컬 warm 기준 순서는 test > build > lint > typecheck다.

합계 행은 **회차별 합의 중앙값**이다. 명령별 중앙값을 더하면 12,496ms가 나오지만 그것은 어느 회차에서도 실제로 관측된 값이 아니므로 쓰지 않는다.

#### `.next` 제거 후 build 1회

| 조건                 | 소요        |
| -------------------- | ----------- |
| `.next` 있음(중앙값) | 3,639ms     |
| `.next` 제거 후      | **3,529ms** |

차이 110ms는 warm 3회의 범위(158ms) 안이라 두 조건의 차이를 가릴 수 없다. `.next` 제거는 1회만 쟀고 로컬 파일시스템·CPU 조건도 러너와 다르므로, **여기서 CI의 build 구간을 추정하지 않는다. 판단 보류.** CI build 소요는 0-5의 측정값으로 확인한다.

#### `pnpm check` 단일 실행과의 비교 (판단 보류)

| 실행 형태                    | 소요         |
| ---------------------------- | ------------ |
| `pnpm check` 단일 1회        | 12,656ms     |
| 개별 호출 회차별 합의 중앙값 | **12,528ms** |

`pnpm check`는 1회만 쟀고 개별 호출은 3회 중앙값이라 회차 수가 다르다. 두 값의 차이 128ms는 개별 호출 합계의 범위(236ms)보다 작다. **계측 분리가 실행 시간에 어떤 영향을 주는지 이 값으로는 판단하지 않는다.** 계측 구성은 Before와 After에 동일하게 적용되므로 비교에는 영향을 주지 않는다.

조건 열은 **잠정값**이다(0-2 참고). 성공 회차는 `Post Set up Node.js` 소요, 실패 회차는 `Set up Node.js`·`Install dependencies` 패턴으로 분류했고, 어느 쪽도 로그로 확정한 것이 아니다.

att10·11은 캐시 미복원 가능성을 시사하는 시간 패턴을 보였고, att12는 저장이 일어난 것으로 보이는 소요를 남겼다. **실제 복원 여부와 그 원인은 미확인이다.** 작성자는 cold 회차(att 1–4) 이후로 캐시를 삭제하지 않았다고 확인했는데 이 구간의 관측과는 맞지 않으며, 기준선에서 제외했다는 사실이 원인 추정을 대신하지는 않는다.

#### cold 3회 (attempt 1~3)

| step                                  | att 1 | att 2 | att 3 | 중앙값   | 범위   |

#### cold 집계 — 표본 범위별 비교 (기준선 미확정)

cold로 분류한 성공은 5회다(att 1·2·3·4·12). 어느 범위를 기준선으로 쓸지에 따라 값이 달라진다.

| 포함 회차  | raw            | 전체 실행 시간 중앙값 | Playwright 중앙값 | 검증 4개 합 |
| ---------- | -------------- | --------------------- | ----------------- | ----------- |
| 1·2·3      | 90 / 114 / 107 | 107s                  | 34s               | 39s         |
| 1·2·3·4    | +90            | 98.5s                 | 29.5s             | 39s         |
| 1·2·3·4·12 | +87            | **90s**               | **25s**           | 39s         |

**사전에 정한 표본 선택 규칙은 없었다.** 요구 최소 회차가 3회라는 사실은 나머지 회차를 제외할 근거가 되지 않는다. 기준선은 아래 둘 중 하나로 정해야 한다.

- 조건이 확인된 유효 표본 전체(5회)를 집계한다.
- 특정 회차를 제외한다면 그 회차의 환경 차이를 제시한다.

**이 결정은 캐시 조건이 로그로 확정된 뒤에 한다.** att12는 조건 분류 자체가 다른 회차보다 불확실한 구간(att10~12)에 있다.

#### 실패 5회 (attempt 7~11)

다섯 회차 모두 `Install Playwright Chromium when used`에서 7초 만에 실패했고, 이후 검증 step은 전부 skip됐다.

```
Err: https://dl.google.com/linux/chrome-stable/deb stable/main amd64 Packages
  Hash Sum mismatch
E: Failed to fetch .../binary-amd64/Packages.gz  Hash Sum mismatch
Failed to install browsers
Error: Installation process exited with code: 100
```

`playwright install --with-deps`가 내부적으로 `apt-get update`를 돌고, 그 과정에서 Google Chrome apt 저장소의 인덱스 해시가 발표값과 어긋났다(Release file created 17:16:59).

다섯 번의 재시도에서 같은 해시 불일치가 반복됐다. 약 30분 뒤 attempt 12에서는 같은 step이 정상 통과했다. 이 구간에서는 재시도로 복구되지 않았으며, 이 workflow에서 사용되지 않는 브라우저 설치 단계 때문에 이후 검증도 실행되지 못했다. 불일치가 어디에서 발생했는지(원본 저장소·미러·전송 구간)는 확인하지 않았다. 확인된 것은 해시 검증이 실패했다는 사실과, **그 실패가 검증 전체를 막은 것은 이 설치 단계를 두고 있는 workflow 구성 때문**이라는 점이다.

#### 병목 지목

`Install Playwright Chromium when used`가 병목이다. 근거는 네 가지가 한 step에 모여 있다.

1. **소요** — 기록된 개별 step 중 가장 오래 걸린다. cold 중앙값 34초, warm 중앙값 26초로 실제 검증 4개의 합(39초)에 육박한다.
2. **변동성** — 성공 8회에서 22~~44초로 흩어진다. 같은 회차의 검증 4개 합은 38~~40초에 모인다. 범위끼리의 비교만으로 전체 변동에 대한 기여도를 계산한 것은 아니다.
3. **무용성** — `pnpm check`에 `test:e2e`가 없어 이 workflow에서 chromium은 실행되지 않는다.
4. **실패 지점** — 패키지 인덱스 해시 검증 실패로 5회(att 7~11) 이 step에서 멈췄고, 이후 검증 step이 모두 skip됐다.

근거는 이 run의 13회 실행이다. 조건 분류가 확정되기 전이라 cold·warm 중앙값은 잠정값이지만, "가장 오래 걸리고 변동이 크며 이 workflow에서 쓰이지 않는다"는 세 가지는 분류와 무관하게 성립한다.

#### 확보하지 못한 것

1. **각 attempt의 캐시 로그** — `Set up Node.js`의 복원 메시지(복원된 key)와 `Post Set up Node.js`의 저장·생략 메시지. 인증 없이는 403이라 읽지 못했다. 추가 실행이 아니라 이미 확보한 13회의 로그를 열면 된다.

## 2단계 — 캐시 동작 확인

> 미착수.

### 확인 절차

1. warm 실행 로그에서 캐시 복원 메시지와 복원된 key를 캡처한다.
2. **캐시 키가 달라지도록** lockfile을 변경하고, 그 실행에서 **실제로 복원이 일어났는지 로그로 확인한다.** 키가 바뀌었다고 반드시 미복원이 되는 것은 아니며, 설정에 따라 다른 key로 부분 복원될 수 있다.
3. 복원된 경우와 되지 않은 경우의 `install` 소요를 함께 기록한다. 다만 의존성이 바뀌면 설치 작업량 자체가 달라지므로, 시간 차 전부를 캐시 효과로 해석하지 않는다.
4. 실험 후 lockfile을 원래대로 되돌린다. 이 변경은 최종 커밋에 남기지 않는다.
