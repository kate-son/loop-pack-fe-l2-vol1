# 10주차 1단계 — CI 파이프라인 측정·최적화

1단계의 0~3단계 실행 기록이다. 측정 조건, 원시값, 실행 로그, 판단 근거를 이 문서 안에 둔다.

| 단계 | 내용                       | 상태                                     |
| ---- | -------------------------- | ---------------------------------------- |
| 0    | Before 고정                | 완료 (cold 4회 / warm 3회)               |
| 1    | 병목에 맞는 전략만 적용    | 완료 — Playwright 설치 제거, concurrency |
| 2    | 캐시 동작 확인             | 완료                                     |
| 3    | 같은 조건에서 After 재측정 | 완료 (cold 4회 / warm 4회)               |

각 단계의 로그 원문(캐시 복원·미복원 메시지)은 인증 없이 403이라 확보하지 못했다. 제출 증거로 덧붙일 몫이다.

**Before 표본**

| 조건 | 회차            | 근거                                                        |
| ---- | --------------- | ----------------------------------------------------------- |
| cold | attempt 1·2·3·4 | 작성자가 실행 전 그 PR의 캐시를 삭제했다고 확인한 회차 전부 |
| warm | attempt 5·6·13  | 캐시를 삭제하지 않고 실행한 성공 회차                       |

attempt 12는 cold로 분류했지만 기준선에서 제외한다. attempt 10~12 구간의 캐시 상태가 작성자의 삭제 기록과 어긋나 조건이 확인된 표본으로 보기 어렵다(0-5 참고).

**보강할 것**: 각 attempt의 `Set up Node.js`·`Post Set up Node.js` 로그(복원된 key, 저장·생략 메시지). 조건은 작성자 기록으로 정해졌고, 로그는 제출 증거로 덧붙인다. 추가 실행 없이 이미 확보한 13회의 로그를 열면 된다.

## 0단계 — Before 고정

### 0-1. 계측 구성 변경

`pnpm check`가 단일 step이라 내부의 test·lint·typecheck·build 소요가 Actions 로그에서 구분되지 않았다. 구간을 보려면 계측이 필요한데, 이를 After에만 넣으면 Before와 조건이 달라져 시간 차의 원인을 가릴 수 없다. 그래서 **Before 측정 시점부터 step을 나누고 After까지 같은 구성을 유지한다.**

`.github/workflows/quality.yml` 변경:

```diff
-      - name: Run quality checks
-        run: pnpm check
+      - name: Test
+        run: pnpm test
+      - name: Lint
+        run: pnpm lint
+      - name: Typecheck
+        run: pnpm typecheck
+      - name: Build
+        run: pnpm build
```

실행 순서와 검증 집합은 `pnpm check`와 같다. `package.json`의 `check` 스크립트는 로컬 실행용으로 그대로 둔다.

같은 커밋에서 job에 `timeout-minutes: 10`을 추가했다. 멈춘 job이 러너를 무한히 잡고 있지 않도록 상한을 두는 것이고, 관측된 최장 실행 시간 114초보다 여유를 두어 10분으로 설정했다. 이 값은 Before와 After에서 동일하게 유지한다.

이 변경으로 `pnpm` 기동이 5회(`check` 1회 + 하위 4회)에서 4회로 줄어든다. **이 차이를 최적화 성과로 계산하지 않는다** — 계측은 Before와 After에 동일하게 적용되므로 두 값 모두에 같은 방향으로 작용한다.

#### 계측 방식을 step 분리로 정한 근거

| 방식                 | 해상도 | 값 회수                                 | 저장소에 남는 계측 코드 |
| -------------------- | ------ | --------------------------------------- | ----------------------- |
| **step 분리** (채택) | 1초    | Actions API, 인증 없이 조회 가능        | 없음                    |
| 로그 타임스탬프 출력 | 밀리초 | raw 로그 열람 필요 (현재 인증 없이 403) | workflow 또는 스크립트  |

이번 단계는 cold·warm 각 3회 이상씩(Before/After 합쳐 최소 12회) 같은 조건으로 반복해 raw·중앙값·범위를 남기는 작업이다. step 분리는 `/actions/runs/{id}/jobs`가 step별 `started_at`·`completed_at`을 돌려주므로 집계가 자동으로 되고, 타임스탬프 방식은 매 회 수동 확인이 붙는다. 반복 횟수가 많을수록 옮겨 적는 과정에서 값이 섞일 여지도 커진다.

**대가**: step 소요가 초 단위로만 기록된다. 실측에서 Typecheck는 4초, Lint는 6초로 나왔는데, 이런 짧은 구간은 ±1초가 비율로 크게 잡힌다. 기록 해상도의 한계이므로 반복 측정으로 줄지 않는다. 구간들이 비슷하게 나와 순위가 갈리지 않으면 타임스탬프 출력을 덧붙여 확인한다.

### 0-2. 측정 조건 고정

Before와 After에서 아래 조건을 모두 동일하게 유지한다. 달라지는 것은 commit SHA, 캐시 상태(cold/warm), 그리고 **1단계에서 의도적으로 적용한 workflow 변경**이다.

#### 트리거와 비교 범위

| 항목      | 고정값                                                              |
| --------- | ------------------------------------------------------------------- |
| 트리거    | `pull_request` 이벤트                                               |
| 비교 범위 | `pnpm check`가 실행하는 검증 집합 (test · lint · typecheck · build) |
| 러너      | `ubuntu-latest`                                                     |
| Node 버전 | `.nvmrc` 기준 (24.17.0)                                             |
| pnpm 버전 | `package.json#packageManager` 기준 (10.15.1)                        |

측정 시작 전 실행 이력은 전부 `push`/`main` 이벤트였고 `pull_request` 실행 이력이 없었다. 측정 대상이 PR 검증이므로 트리거를 PR로 통일한다.

**E2E는 이 단계의 비교 범위에 넣지 않는다.** 검증 항목이 늘어나면 실행 시간 변화가 최적화의 결과인지 작업량 증가의 결과인지 구분되지 않는다. E2E 추가는 **과제 2단계 — 조건부 실행 설계**에서 다룬다.

#### cold / warm 정의

측정 대상은 **PR #1의 CI 실행**이고, 조작 대상은 **그 PR의 캐시(`refs/pull/1/merge` 스코프)**다.

| 조건 | 준비                              |
| ---- | --------------------------------- |
| cold | 해당 PR의 캐시를 삭제한 뒤 실행   |
| warm | 해당 PR의 캐시를 유지한 채 재실행 |

측정할 때마다 **삭제한 캐시의 key와 id를 기록한다.** 조건이 실제로 성립했는지는 그 실행의 캐시 복원·미복원 로그로 확인한다.

#### 조건 분류 근거와 로그 증거 보강

**분류의 근거는 작성자 기록이고, 로그는 제출 증거로 덧붙일 몫이다.** 아래 표의 첫 항목이 분류를 정했고, 나머지는 그와 어긋나지 않는지 대조한 정황이다. 어느 것도 저장·복원 분기가 실행됐다는 직접 증거는 아니다.

**보강할 로그** — `actions/setup-node`는 복원된 key가 primary key와 같으면 저장을 생략하고 그 이유를 로그에 남긴다. `Set up Node.js`의 복원 메시지(복원된 key)와 `Post Set up Node.js`의 저장·생략 메시지가 회차별 조건의 직접 증거가 된다. **이 로그는 인증 없이 403이라 아직 확보하지 못했다.**

| 정황                       | 내용                                                                                      |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| 작성자 확인                | cold 회차(att 1~4)는 재실행 전에 매번 캐시를 삭제했고, 이후 회차는 삭제하지 않았다        |
| `Post Set up Node.js` 소요 | 4–6초인 회차와 0초인 회차로 갈린다. 저장이 일어났는지 시사하지만 소요 시간일 뿐이다       |
| PR 캐시 생성·접근 시각     | `created 18:14:57`는 att12 종료 시점, `last_accessed 18:16:25`는 att13 실행 구간과 겹친다 |
| 시간 패턴                  | cold로 분류한 회차는 `Set up Node.js` 5–6s·`Install` 5–7s, warm은 8–12s·2s                |

**시간 패턴만으로 조건을 판별하면 캐시 효과 분석이 순환한다** — 시간으로 조건을 나눈 뒤 그 시간 차이를 캐시 효과로 설명하는 구조가 되기 때문이다. 그래서 조건은 작성자 기록으로 정하고, 시간 패턴은 대조에만 쓴다.

#### 기록 항목

| 항목              | 설명                                                     |
| ----------------- | -------------------------------------------------------- |
| 전체 실행 시간    | job 시작부터 종료까지 (대기열 시간은 포함하지 않는다)    |
| 러너 총 사용 시간 | 모든 job의 소요 합 (job을 나누면 이 값과 위 값이 갈린다) |
| step별 소요       | Actions API의 step `started_at`·`completed_at`           |
| 캐시 복원 결과    | 복원 여부, 복원된 key, 복원 메시지                       |
| 실행 식별자       | run URL, run ID, attempt 번호                            |
| commit SHA        | Before/After 각각                                        |
| 삭제한 캐시       | cold 실행 시 지운 key와 ref                              |

cold 3회 이상 / warm 3회 이상을 각각 재고 **raw 값·중앙값·범위**를 모두 남긴다. GitHub 러너 성능이 실행 시점에 따라 흔들리므로, 1회 값으로는 이후 변화가 개선인지 측정 흔들림인지 구분되지 않는다. Before와 After 모두 이 회차 수를 유지한다.

### 0-3. 측정 전 확인한 사항

- Actions 실행 이력 7회는 전부 `push`/`main` 이벤트이고 `pull_request` 실행 이력이 없다.
- PR 첫 실행 뒤에는 그 PR의 캐시가 새로 생기므로, cold 회차마다 이 캐시를 삭제한다. 조건 성립 여부는 그 실행의 캐시 복원 로그로 확인한다(0-2 참고).
- `concurrency` 설정이 없다. 같은 PR에 연속 push가 들어오면 이전 실행이 그대로 남는다.

#### 측정 저장소를 fork로 두는 이유

과제 제출은 upstream(`loopers-labs`)에 PR을 여는 방식인데, 그곳은 수강생 공용 저장소라 측정에 맞지 않는다. 확인 시점에 다른 PR의 캐시 19개가 있었고, 캐시 삭제 권한이 없어 **cold 조건을 만들 수 없다.** 다른 PR의 캐시를 지우는 것도 하면 안 되는 일이다. 동시 실행이 많아 러너 조건도 흔들린다.

그래서 0-5의 Before/After 측정은 **fork(`kate-son`)에서 연 PR로 수행한다.** 과제가 요구하는 것은 같은 조건에서 잰 Before/After이고, 측정 저장소가 fork라는 사실은 여기에 기록해 둔다. 제출 PR은 upstream에 별도로 연다.

### 0-4. 로컬 사전 확인 (참고값)

목적은 두 가지다. 네 명령이 분리된 상태에서 모두 통과하는지 확인하는 것, 그리고 구간 비율의 대략을 미리 보는 것이다. **Before 값이 아니며, CI 측정과 직접 비교하지 않는다.**

| 항목      | 값                                    |
| --------- | ------------------------------------- |
| 기준 커밋 | `051307a4` + 워크플로 변경(작업 트리) |
| Node      | v24.17.0                              |
| pnpm      | 10.15.1                               |
| OS·CPU    | macOS 26.5 / Apple M5 (arm64, 10코어) |
| 캐시 상태 | warm (`node_modules`·`.next` 존재)    |

#### 구간별 소요 — 3회

| 명령             | run 1   | run 2   | run 3   | 중앙값       | 범위  |
| ---------------- | ------- | ------- | ------- | ------------ | ----- |
| `pnpm test`      | 6,027ms | 6,063ms | 6,104ms | **6,063ms**  | 77ms  |
| `pnpm lint`      | 1,901ms | 1,863ms | 1,958ms | **1,901ms**  | 95ms  |
| `pnpm typecheck` | 876ms   | 893ms   | 920ms   | **893ms**    | 44ms  |
| `pnpm build`     | 3,724ms | 3,566ms | 3,639ms | **3,639ms**  | 158ms |
| 회차별 합계      | 12,528  | 12,385  | 12,621  | **12,528ms** | 236ms |

세 회차 모두 네 명령이 통과했다. 로컬 warm 기준 순서는 test > build > lint > typecheck다.

합계 행은 **회차별 합의 중앙값**이다. 명령별 중앙값을 더하면 12,496ms가 나오지만 그것은 어느 회차에서도 실제로 관측된 값이 아니므로 쓰지 않는다.

#### `.next` 제거 후 build 1회

| 조건                 | 소요        |
| -------------------- | ----------- |
| `.next` 있음(중앙값) | 3,639ms     |
| `.next` 제거 후      | **3,529ms** |

차이 110ms는 warm 3회의 범위(158ms) 안이라 두 조건의 차이를 가릴 수 없다. `.next` 제거는 1회만 쟀고 로컬 파일시스템·CPU 조건도 러너와 다르므로, **여기서 CI의 build 구간을 추정하지 않는다. 판단 보류.** CI build 소요는 0-5의 측정값으로 확인한다.

#### `pnpm check` 단일 실행과의 비교 (판단 보류)

| 실행 형태                    | 소요         |
| ---------------------------- | ------------ |
| `pnpm check` 단일 1회        | 12,656ms     |
| 개별 호출 회차별 합의 중앙값 | **12,528ms** |

`pnpm check`는 1회만 쟀고 개별 호출은 3회 중앙값이라 회차 수가 다르다. 두 값의 차이 128ms는 개별 호출 합계의 범위(236ms)보다 작다. **계측 분리가 실행 시간에 어떤 영향을 주는지 이 값으로는 판단하지 않는다.** 계측 구성은 Before와 After에 동일하게 적용되므로 비교에는 영향을 주지 않는다.

#### 병목 지목

`Install Playwright Chromium when used`가 병목이다. 근거는 네 가지가 한 step에 모여 있다.

1. **소요** — 기록된 개별 step 중 가장 오래 걸린다. 기준선 기준으로 cold 중앙값 29.5초, warm 중앙값 26초이고, 실제 검증 4개의 합(39초)에 가깝다.
2. **변동성** — 성공 8회에서 22–44초로 흩어진다. 같은 회차의 검증 4개 합은 38–40초에 모인다. 범위끼리의 비교만으로 전체 변동에 대한 기여도를 계산한 것은 아니다.
3. **무용성** — `pnpm check`에 `test:e2e`가 없어 이 workflow에서 chromium은 실행되지 않는다.
4. **실패 지점** — 패키지 인덱스 해시 검증 실패로 5회(att 7~11) 이 step에서 멈췄고, 이후 검증 step이 모두 skip됐다.

근거는 이 run의 13회 실행이다. "가장 오래 걸리고 변동이 크며 이 workflow에서 쓰이지 않는다"는 세 가지는 cold·warm 분류와 무관하게 성립한다.

## 1단계 — 병목에 맞는 전략만 적용

> 완료. 0-5의 병목 지목에 대응하는 것만 적용하고, 검토했으나 적용하지 않은 것은 이유와 함께 남겼다.

### 검토 대상과 결정

### 1단계에서 하는 일과 하지 않는 일

**하는 일** — 쓰이지 않는 Playwright 설치를 **제거**한다. 검증 집합(test·lint·typecheck·build)은 Before와 동일하게 유지된다.

**하지 않는 일** — E2E를 CI에 추가하지 않는다. 추가하면 Before와 검증 집합이 달라져 시간 변화를 최적화의 결과로 읽을 수 없다. E2E 실행 환경과 그에 필요한 브라우저 설치는 **과제 2단계 — 조건부 실행 설계**에서 다룬다.

### `concurrency` 설정안

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

- 그룹 키에 `github.ref`를 넣지 않으면 PR 실행 취소가 `main` push 실행까지 끌고 간다.
- `cancel-in-progress`를 PR로 한정하면 **`main`의 실행 중인 작업은 취소되지 않는다.** 다만 같은 그룹에서 대기 중인 실행은 새 실행이 들어오면 교체될 수 있다. 이 설정이 보장하는 것은 진행 중 작업의 보호까지다.

**측정과의 관계**: concurrency가 켜져 있으면 실행이 겹칠 때 취소·대기가 생길 수 있다. 그래서 After 측정은 **한 회차가 끝난 뒤 다음 회차를 시작하고, 취소된 실행은 정상 완료 시간 집계에서 제외한다.** concurrency의 효과는 실행 시간이 아니라 **연속 push 시 이전 실행이 취소되는지**로 따로 확인한다.

### After 측정 계획

한 세트는 **cold 3회 + warm 3회 = 6회**다. Before와 같은 조건·집계 방식(중앙값·범위)을 쓴다.

| 항목        | 값                                                                                                                         |
| ----------- | -------------------------------------------------------------------------------------------------------------------------- |
| 적용할 변경 | Playwright 설치 제거 + `concurrency` 그룹                                                                                  |
| 측정 회차   | 각 조건 최소 3회 (cold 3 + warm 3 = 6회)                                                                                   |
| 시간 해석   | 전체 시간 차이를 미리 한 변경에 귀속하지 않는다. **제거된 구간과 나머지 step의 변화를 Before와 나란히 비교**한 뒤 서술한다 |
| 별도 확인   | concurrency의 중복 실행 취소 동작 — 실행 시간이 아니라 연속 push 시 이전 실행이 취소되는지로 본다                          |

## 2단계 — 캐시 동작 확인

### 실험 방법

`pnpm-lock.yaml`을 재생성해 `actions/setup-node`의 캐시 key가 달라지게 했다. key에 lockfile 해시가 들어가기 때문이다.

| ------------------- | -------------------------------------------------------- |
| 변경 방법           | `pnpm add -D prettier@3.9.4` — 해석 버전만 3.9.5 → 3.9.4 |
| `package.json` 명세 | `^3.9.4` 그대로. 설치되는 실제 버전만 달라진다           |

| 원복                | 실험 후 lockfile을 실험 전 커밋 상태로 되돌렸다          |

### 읽은 것

#### `main` 실행 보호 — 설정 근거와 검증 상태

**설정 근거**: `pull_request` 이벤트의 `github.ref`는 `refs/pull/<번호>/merge`이고 `push`/`main`은 `refs/heads/main`이다. 그룹 키에 `github.ref`가 들어가므로 두 이벤트는 **서로 다른 그룹**으로 계산된다. 다른 그룹의 실행은 취소 대상이 되지 않는다. 또한 `cancel-in-progress`가 `push` 이벤트에서는 `false`라, `main` 실행끼리도 서로 취소하지 않는다.

**실행 검증**: 아직 하지 않았다. 확인하려면 **`main` 실행이 도는 동안 PR 실행을 추가**해 `main` 실행이 살아남는지 보는 방향이 목적에 맞다. 반대로 PR 실행 중에 `main`에 push하는 것은, 새 `main` 실행의 `cancel-in-progress`가 `false`라 애초에 취소가 일어나지 않으므로 검증이 되지 않는다.

이 확인만을 위해 `main`에 불필요한 변경을 만들 필요는 없다. 위 설정 근거와 검증 미실시를 구분해 기록해 둔다.
